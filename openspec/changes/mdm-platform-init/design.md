## 背景

在若依前后端分离版（Spring Boot 2.5.15 单体 + Vue3/TS 前端）之上构建主数据管理平台。见 proposal.md - Why/What：新增六大主数据能力，复用若依 RBAC、字典、参数、日志与代码生成器底座。本设计覆盖模块划分、动态建模存储、审核、编码、分发等关键技术决策。

## 目标与非目标

**目标**

- 六大能力域（模型、编码、标准、维护、质量、分发）落地为可发布的 **1.0.0** 版本
- 模型驱动：新增数据对象通过配置即可生成维护界面，无需为每个对象编写一套 CRUD
- 保持若依单体架构与 MySQL + Redis 中间件栈，不新增外部依赖
- 开发周期 8 周，第 6 周完成首期演示，第 8 周末发布 1.0.0

**非目标**

- 不做微服务拆分（后续演进 RuoYi-Cloud 时 mdm 模块可整体搬迁，见 1.1.0 展望）
- 不集成 Flowable/Activiti 工作流引擎
- 不做跨系统实时同步协议设计（分发以 API 推送 + 记录重放为主）
- 不做主数据质量大屏/报表（规划于 1.1.0）

## 设计决策

### 决策一：独立 Maven 模块 `ruoyi-modules/mdm`

新增 `ruoyi-modules/mdm`，下分六个子包（model、coderule、standard、maintenance、quality、distribution），以 Maven 依赖方式挂入 ruoyi-admin 主应用。

- **理由**：与 ruoyi-system 解耦，包边界清晰；未来迁移微服务可整模块搬迁；独立 `mdm_*` 表空间便于运维识别
- **备选**：并入 ruoyi-system —— 开发更省事，但耦合系统管理，MDM 专属逻辑混杂
- **代价**：需在 ruoyi-admin/pom.xml 增加依赖

### 决策二：动态模型 → 发布时生成物理业务表

元数据落表（`mdm_object` 对象、`mdm_attribute` 属性、`mdm_category` 分类），数据对象**发布**时动态创建物理表 `mdm_data_<obj_code>`（属性列 + 通用列：id、编码、状态、版本、审核信息、审计字段）。维护 CRUD 通过 MyBatis 动态 SQL 按元数据拼接。

- **理由**：主数据查询是核心高频路径，物理表可加索引、SQL 直观；契合若依 MyBatis 生态；相比 EAV 避免"面条查询"与性能陷阱
- **备选**：EAV 实体-属性-值 —— 建模灵活但查询、约束、索引困难；JSON 列 —— 灵活但难以做关系查询与唯一约束
- **代价**：模型变更需 DDL（ALTER TABLE），见决策六缓解

### 决策三：审核流程用内置轻量实现

`mdm_audit_flow` 配置启用/禁用与审核角色；待审变更存 `mdm_audit_task`（含变更前后数据快照），状态机：草稿 → 待审核 → 生效 / 驳回。不引入工作流引擎。

- **理由**：MDM 审核场景为单一"提交→通过/驳回"，轻量内置足够；Flowable 增加依赖、表结构与学习成本
- **备选**：Flowable/Activiti —— 适合复杂多级会签场景，当前 YAGNI，1.1.0 视需求引入

### 决策四：编码生成用 Redis INCR + 分段规则

`mdm_code_rule` 存分段配置（常量/日期/流水/属性值），流水号用 Redis `INCR`（键含对象编码与周期前缀，支持按日/月/年/不重置），按段拼接生成编码。

- **理由**：Redis INCR 原子、跨实例一致、性能高；周期重置即换键；配合数据库唯一索引兜底防重
- **备选**：数据库流水表 + 行锁 —— 简单但并发瓶颈；纯自增 —— 无法定制分段与可读性
- **兜底**：业务表编码列加唯一索引，极端冲突时重试

### 决策五：分发内嵌分发器，不引入 MQ

`mdm_distribution` 配置订阅方与触发策略（变更即推 / 定时）；变更后由内嵌分发器调用订阅方 API，结果写 `mdm_distribution_record`，失败可查询重推。

- **理由**：第一期订阅方数量少、流量低，内嵌实现避免引入 RabbitMQ 的部署与运维负担
- **备选**：RabbitMQ 异步削峰 —— 订阅方规模扩大或推送量大时再引入，分发器接口保留扩展点（1.1.0）
- **代价**：订阅方不可用会影响主流程（同步推送），故第一期默认**异步线程推送** + 失败重试

### 决策六：模型变更版本化

对象模型增加版本号；已发布模型仅允许"新增可空/带默认值属性"后重新发布（生成 ALTER TABLE ADD COLUMN），不允许删除/改类型已生效属性。破坏性变更需"新建对象版本"走发布。

- **理由**：避免动态 DDL 破坏存量数据与下游契约
- **代价**：模型调整灵活性受限，换取数据安全

### 决策七：对外接口用应用凭证鉴权

`mdm_app` 注册订阅方，生成 appid/secret；对外查询/推送确认接口使用 appid + 签名（或短期 token）鉴权，不走用户登录体系。

- **理由**：下游系统是机器对机器，复用若依用户登录不现实
- **备选**：开放网关统一鉴权 —— 当前无独立网关，单体版内嵌实现

## 风险与权衡

- [动态 DDL 风险] → 决策六版本化：仅新增可空/默认值字段；DDL 失败事务回滚并保留对象为"发布失败"
- [分发失败阻塞主流程] → 异步推送 + 记录表 + 重试/重推；订阅方超时与熔断阈值可配置
- [动态 SQL 注入面] → 对象/属性编码白名单校验（仅允许元数据中已发布标识），SQL 全部参数化
- [编码并发唯一性] → Redis INCR 原子 + 业务表唯一索引兜底
- [模型驱动导致页面通用化、交互体验弱于定制页] → 第一期接受通用维护页；高价值对象后续可定制页面

## 迁移计划

- **数据库**：新增 `sql/mdm/*.sql`（元数据表 + 种子字典/菜单），不修改若依原有表
- **部署**：mdm 模块随 ruoyi-admin 主应用一并打包发布；前端新增 mdm 菜单路由
- **回滚**：停用 mdm 菜单与 `/mdm/**` 接口路由即可，若依既有功能完全不受影响；新增表可保留
